## 1. 加固总览：三层结构

```
┌─────────────────────────────────────────────────────────────┐

│                                                             │
│  AndroidManifest.xml            明文！Application 指向壳      │

│  assets/nedata.db   61.7 MB     ← 真身：全加密，熵 8.0        │
│  libnesec.so        953 KB      ← 解密器（假段表 + 反调试）    │

└─────────────────────────────────────────────────────────────┘
              │
              ▼  运行期：解密 → 只在内存里存在
┌─────────────────────────────────────────────────────────────┐
│  真实 Java 代码（26,854 个类）                                │
```

| 层 | 载体 | 保护对象 | 蓝队手段 | 红队结论 |
|---|---|---|---|---|

| **L2 native 加固** | `libnesec.so` | 解密器自身 | 假段表、字符串加密、动态注册、反调试 | 反调试有效；但破解它没必要 |
| **L3 风控网络** | `libNetHTProtect.so` | 服务端信任链 | 段头混淆、XZ 壳、设备指纹 | 真正的对抗面在这一层 |

## 2. L1 · DEX 整体加密（壳）

### 2.1 静态形态：APK 里只有一个 85 KB 的 dex

```
classes.dex   85280 字节
SHA-256       1c1685dc74c8f3066a705bc2ecc23eb8077eb791fd4914c37b1cbc086cb0945e
```

一个 26,854 类的 App，dex 不可能只有 85 KB。这 85 KB 里装的是壳自己的类（dex 内字符串实测）：

```
com/netease/nis/wrapper/Entry
com/netease/nis/wrapper/MyApplication
com/netease/nis/wrapper/MyJni
com/netease/nis/wrapper/NEDialog
com/netease/nis/wrapper/Utils
com/netease/nis/wrapper/a  …  i
```

`AndroidManifest.xml` 里：

```xml
<application android:name="com.netease.nis.wrapper.MyApplication" …>
```

**壳直接接管了进程入口。** App 真正跑起来的第一段代码是壳的。

### 2.2 真身：`assets/nedata.db`

| 检查项 | 实测值 | 判读 |
|---|---|---|
| 大小 | 64,673,134 B（61.7 MB） | 与真 dex 体量吻合 |
| 文件头（hex） | `1e ee 5a 96 18 aa 5d 2a 82 1f 50 15 …` | **自定义魔数** |
| 熵值（前 1 MB） | **8.000** | 完全加密（明文数据典型 4–6） |
| `dex\n0` magic | **0 次** | 无任何明文 dex |
| `PK\x03\x04` | **0 次** | 不是 zip |
| `SQLite` | **0 次** | 名字叫 `.db` 是伪装 |

**结论**：真 dex 全部在这个加密容器里，命名 `nedata.db` 是为了让静态扫描器认为它是数据库文件而跳过。

### 2.3 运行时形态：内存加载，不落盘

设备侧实测（`cn.neoclub.uki`，uid `10420`）：

```
/proc/<pid>/maps 里没有独立的 dex 文件映射
JDWP/ART 层出现：Anonymous-DexFile@3534234116.vdex
```

`Anonymous-DexFile` 是 ART 对**内存构造的 dex** 的命名。也就是说：

> 壳读出 `nedata.db` → 用 native 解密 → 在内存里拼成合法 dex → 交给 `InMemoryDexClassLoader` / `DefineClass` 加载。**全过程不写磁盘。**

这解释了两件事：

1. **为什么静态反编译一个业务类都看不到** —— APK 里根本没有。
2. **为什么只在内存里能抠出来** —— 我们最终从 `/proc/<pid>/mem` 里捞出了 **22 份第三方 SDK dex、合计 118 MB**。

### 2.4 蓝队设计意图 / 红队突破点

| 蓝队想要 | 实际效果 | 红队怎么破 |
|---|---|---|
| 让静态分析拿不到代码 | 有效：jadx 直接打开 APK 只能看到 29 个壳类 | 放弃静态，改**运行时内存取证**（§5.2） |
| 让代码不落盘，躲过文件扫描 | 有效：磁盘上永远找不到解密后的 dex | 在**解密之后、加载之前**的时间窗口插进去（LSPosed 天然在那个位置） |
| 加大脱壳成本 | 只挡住批量自动化，挡不住定向单点 | 定向分析只需**一台 root 设备 + 一个 hook 框架** |

## 3. L2 · native 加固（`libnesec.so`）

```
libnesec.so   953,424 字节
SHA-256       8deb69cccfc1542050d3ea6c2a2a0abcc34a4017f3f6b94b3324d40f834836c7
熵（前 1MB）  7.417
```

这是壳的大脑。四层防护：

### 3.1 假段表 —— 标准 `.text` 只有 16 字节

实测节表（纯 Python 读 ELF，无需 NDK）：

```
.text           size=16          ← 只有一条跳转
.gnu.fragment   size=802416      ← 真身，占全文件 84%
.gnu.draft      size=71320
.gnu.stub       size=8704        ← 解密 stub
.eh_intent      size=8           ← 非标准段名
.gnu.stub / .gnu.fragment / .gnu.draft / .eh_intent 全部不是标准段
```

蓝队用一个**私有段名体系**把真正的代码藏进 `.gnu.fragment`，让所有按 `.text` 定位代码的工具（IDA 自动分析、基于段的特征扫描）看到一片空白。

### 3.2 字符串全加密

`libnesec.so` 共 5,948 条可打印字符串，**没有一条可读**：

```
=Y)>!W     T{hw@v     2op,Xx<8   v'J|E4}z   8;kpj
V3lBk`     +4?UfFvn   jst:mn     \?V]r@     z6P!P^d
```

对比：App 自己的 `libuki_base_jni_tool.so` 字符串是明文的，我们的签名盐值 `4E4C92882808141E2E9C51DB38CA095B` 就是从那里面读出来的。

> **推论**：易盾只加固**自己的库 + 业务 dex**，不碰业务自带的 native 库。这是它的成本边界，也是红队的便宜。

### 3.3 动态注册 —— 0 个 JNI 导出

`.dynsym` 里 `Java_*` 符号数量：**0**。

所有 JNI 入口用 `RegisterNatives` 在运行时注册。静态搜 `Java_com_netease_...` 一无所获，`frida-trace -j` 也列不出目标。

### 3.4 能力面（导入函数暴露的意图）

| 导入符号 | 用途 | 对抗含义 |
|---|---|---|
| `popen` `pclose` `sysconf` `uname` `readlink` `getenv` | 环境探测 | 执行 shell 命令查 root、查挂载、读 `/proc` |
| `mprotect` `mmap` `munmap` | 内存权限切换 | 解密后把数据段改成**可执行**（RWX），自修改代码 |
| `sigaction` | 接管信号 | **信号级反调试**：吃掉 SIGTRAP/SIGSEGV，让调试器断不下来或断下就崩 |
| `dlopen` `dlsym` `dladdr` | 动态解析 | 把真实导入藏起来，静态看不到"调了谁" |

### 3.5 蓝队设计意图 / 红队突破点

| 蓝队想要 | 实际效果 | 红队怎么破 |
|---|---|---|
| 隐藏反调试逻辑 | 有效：字符串加密 + 动态注册，静态找不到检测代码 | 不拆它，**绕开它**（换插桩层，见 §5.1） |
| 让调试器无法驻留 | 有效：frida attach 2–3 秒后进程干净退出 | 不跟它抢 ptrace，改用 **LSPosed 模块**（在 Zygote fork 后、壳初始化前就已注入） |
| 让自动化脱壳工具失效 | 有效：通用脱壳机（fart、youpk 等）打不过假段表 | 定向分析：**只取需要的那个类/方法**，不全量脱 |

## 4. L3 · 风控 / 网络层（`libNetHTProtect.so`）

```
libNetHTProtect.so  4,972,784 字节
SHA-256             67bf5cae959ef45b4c6588529cdbbdc80ef60d9935c3f2ee858e12497ff0c31f
熵（前 1MB）        6.080
```

### 4.1 识别特征

库内明文串直接给出了它的身份：

```
com/netease/htprotect/factory/JNIFactory
XzUnpacker_IsStreamWasFinished        ← 内部还套一层 XZ 压缩壳
```

**段头混淆**（正常段名被替换成乱码）：

```
x    J    \x01    \x06    ELF\x02\x01\x01
```

同样 **0 个 JNI 导出**。

### 4.2 它到底防什么 —— 这层不是"保护代码"

`htprotect` 是**风控/反爬**模块，不是代码混淆模块。它的目标是：

1. **设备指纹**：采集硬件、系统、安装环境特征，生成设备 ID（就是请求头里那个 32 位 hex 的 `ukiDevice` 的来源体系）
2. **请求风控**：给每个请求算风险分，配合服务端判断"这是人还是脚本"
3. **验证码/挑战**：库里有 `nis_captcha_anim_loading` 这类资源引用

> **重要**：这一层才是真正意义上的"红蓝对抗正面战场"。L1/L2 只是提高**分析成本**；L3 直接参与**服务端信任判定**——决定一个请求能不能过。
>
> 我们打的那个 `x-sign` 签名算法，就落在这条信任链上：`libuki_base_jni_tool.so` 里的 native 函数算签名，而 `ukiDevice` 属于易盾的指纹体系。

### 4.3 红队突破点

| 目标 | 手段 |
|---|---|
| 拿到签名算法 | 逆业务自己的 native（它没加固），别去逆 `htprotect` |
| 拿到设备指纹的生成规则 | hook `JNIFactory` 的调用方（Java 层），比逆 native 便宜得多 |
| 绕过风控判定 | 不绕：**照它要的值给**——把真机抓到的合法值固定下来复用（实测 `ukiDevice` 既不参与签名也不被服务端校验） |

### 5.2 内存取证（击穿 L1 的具体做法）

app 自身 `/proc/self/mem` 会因 SELinux 拿到 EACCES，所以**不在 app 内读**，改由 **root 主机侧**读：

```bash
# 1) 找目标进程
adb shell "pidof cn.neoclub.uki"

# 2) 列内存区间（只看 r-- 且非文件映射的大块）
adb shell "su -c 'cat /proc/<pid>/maps'"

# 3) 按区间 dd 出来，直接在设备上 grep dex 魔数（避免把 200MB 拉回主机）
adb shell "su -c \"dd if=/proc/<pid>/mem bs=4096 skip=<start/4096> count=<len/4096> \
  2>/dev/null | grep -abo 'dex' | head -20\""

# 4) 定位到偏移后，再从主机把那一块拉回来
adb shell "su -c 'dd if=/proc/<pid>/mem bs=1 skip=<off> count=<size>' " > carve.bin
```

要点：
- **保持 SELinux Enforcing**，不 `setenforce 0`，不污染设备安全状态
- 用 `grep -abo` 在**设备侧**过滤，只把命中块拉回主机——200 MB 全拉会超时
- 抠出来的 dex 直接喂 jadx，业务代码就回来了

### 5.3 为什么不打 ptrace 战争

| 方案 | 结果 | 原因 |
|---|---|---|
| frida attach | 失败 | 检测手段多且不在明处（字符串加密 + 动态注册），你补一个洞它换一个 |
| 降级 frida 版本 | 失败 | 检测与版本无关 |
| 自己写 ptrace 反-反调试 | 不可行 | 对方在 **init 阶段**就布防，你的代码还没跑起来就被判了；且不断加检测点，成本无上限 |
| **换插桩层（LSPosed）** | **成功** | 注入时机在 Zygote fork 后，**先于壳的初始化**，且不在 ptrace 维度上对抗 |

**核心判断：不要在你弱势的维度上跟对手拼。** 壳在 native/ptrace 维度强，那就换到**框架层**去打。

## 6. 解决方法（分层绕过方法论）

### 6.1 第一原则：绕过 > 破解

```
破解：把 .gnu.fragment 解密算法逆出来 → 全量还原 dex
      代价：VMP + 假段 + 字符串加密三件套叠加，工作量以「周」计
      收益：一次性拿到全部代码 —— 但定向分析根本不需要全部

绕过：让壳自己解密，在它解密完之后插进去
      代价：一个 root 设备 + 一个 LSPosed 模块，以「小时」计
      收益：你要哪个类就有哪个类，且随版本更新天然兼容
```

**定向任务永远选绕过。** 只有做通用脱壳产品才值得选破解。

### 6.2 分层对应表

| 层 | 蓝队手段 | 对应打法 |
|---|---|---|
| L1 DEX 加密 | 内存加载不落盘 | ① 插桩层注入（LSPosed）→ ② 内存 carve（dd + grep）→ ③ jadx 反编译 |
| L2 native 加固 | 反调试 / 假段 / 动态注册 | **不碰它**。换插桩层绕开；需要 native 细节时用 capstone 静态读业务自己的 `.so` |
| L3 风控网络 | 设备指纹 + 请求风控 | 拿**真机跑出来的合法值**固化复用；算法从**业务调用方**（Java 层）hook，不从风控库里逆 |
| 服务端判定 | 各种错误码 | 把服务端当**活体判定器**做对照实验（见 6.3） |

### 6.3 把服务端当活体判定器

这是整套方法里性价比最高的一招。用错误的凭证去换**不同阶段**的错误码，就能反推服务端的校验顺序与规则：

| 服务端返回 | 卡在哪一步 | 说明 |
|---|---|---|
| `400 Invalid signature` | 签名 | 还没到看 token |
| `401 authorization failed` | token | 签名已通过 |
| `403 Request expired` | 时间戳 | 签名 + token 都通过 |
| `200 {"code":10002,"message":"user not exists"}` | 业务参数 | 校验链全过，只是目标不存在 |
| `200 {"code":0,"message":"success"}` | 全通 | — |

有了这张表，**每次实验都能定位到"错在哪一层"**，不用猜。签名算法就是靠 3–4 组对照实验反推出来的（包括"签名原文用大写 body、发送用原样 camelCase"这种反直觉细节）。

## 8. 红蓝对抗视角

### 8.1 蓝队（加固方）的假设与代价

蓝队的账是这么算的：

```
加固收益 = Σ(抬高的分析成本) × (攻击者数量)
加固成本 = 研发 + 兼容性风险 + 性能损耗 + 售后
```

它的三个隐含假设：

| 假设 | 何时成立 | 何时失效 |
|---|---|---|
| 攻击者是**批量自动化**（爬虫、脱壳机、灰产打包） | 成立 —— 假段表 + 内存加载足以让 99% 的自动化失效 | 对**定向单点分析**几乎无效 |
| 攻击者**没有 root 设备** | 成立 —— 无 root 拿不到 `/proc/pid/mem` | 一台 root 机就归零 |
| 攻击者**会从静态入手** | 成立 —— 大部分人的第一反应是拖进 jadx | 一旦意识到"看内存"，防线形状就变了 |

**结论：这类壳的真实作用不是"防住"，而是「把攻击者分成两队」** —— 把 99% 的自动化流量挡在门外，把成本压到只对少数定向分析者失效。这是**经济学防御**，不是密码学防御。

### 8.2 红队（分析方）的杠杆

红队的账是这么算的：

```
找到「信任链上最便宜的一环」= 用最小代价撬动最大收益
```

本案的信任链与代价对比：

| 环节 | 破解成本 | 我们的选择 |
|---|---|---|
| 网易易盾 native VMP | 极高（周级） | ✗ 不打 |
| 壳的解密算法 | 高 | ✗ 不打 |
| **业务自己的 native 签名函数** | **低**（字符串表直接读盐） | ✓ **打这个** |
| **Java 层调用点** | **低**（hook 拦截器） | ✓ **打这个** |
| **服务端判定逻辑** | **低**（对照实验） | ✓ **打这个** |

> 一句话：**蓝队加固的是"最难的一环"，红队打的是"最便宜的一环"，而这两者通常不是同一个。**

### 8.3 为什么"解密后的那一刻"是永恒突破口

内存加载型壳有一个**结构性缺陷**：

```
密文（磁盘） ──解密──▶ 明文（内存） ──加载──▶ 执行
              ▲                      ▲
              │                      │
         壳的控制区              只能是明文
```

执行引擎要求明文，所以**在内存里必然存在一段明文窗口**。任何在设备上有足够权限的观察者（root、内核模块、Zygote 层注入）都能在那个窗口里取走数据。

这跟 DRM、跟游戏反作弊是**同一个问题结构**：只要最终要在**用户可控的硬件上**执行明文，就存在可观测窗口。这是**理论上限**，不是实现疏漏。

### 8.4 如果对抗升级，会发生什么（推演）

| 蓝队的下一步 | 红队的对应 |
|---|---|
| 检测 LSPosed / Xposed 框架 | 换内核级 hook（KernelSU 模块）、改包名与特征、往内核里放 |
| 校验 SELinux 上下文 / 挂载表 | 保持 Enforcing 下的合法通道，或内核模块直读 |
| TEE / 硬件 attestation（密钥出不了安全区） | 转向**服务端逻辑**与**协议层**，不再打客户端密钥 |
| 把关键算法放服务端 | 对抗面移到**协议与业务逻辑**——这已经是攻防的另一场战争 |
| 加完整性校验 + 远程证明 | 成本直线上升，最终**仍然挡不住一次性的定向分析** |

**趋势判断**：客户端加固的终局是"提高成本"而非"达成安全"。真正的对抗会移到**服务端与协议**。

### 8.5 本案的定性结论

| 维度 | 结论 |
|---|---|
| 加固水平 | **中上**：三层结构完整，反调试真实有效，内存不落盘做得干净 |
| 防护效果 | **对批量自动化有效，对定向分析无效** —— 2 小时内完成从壳到签名的全链路 |
| 最大结构弱点 | 只保护自己的段，**不保护业务自带 native / Manifest / 内存明文窗口** |
| 对抗启示 | 蓝队的成本是**线性**的（每加一层要付兼容性和性能代价），红队的成本是**台阶跳变**的（换一个维度可能一步跨过） |

## 9. 可复用的方法论（下次直接套）

```
第 0 步  先看 App 自己有没有日志/调试开关 —— 比反编译便宜一个数量级
第 1 步  静态看一眼：APK 里的 dex 是不是只有壳类？
         是 → 判定为「DEX 加密型壳」，直接走第 2 步（别在静态上耗时间）
第 2 步  上 root 设备 + LSPosed，模块注入（不要死磕 frida）
         验证：进程不自杀 = 绕过反调试成功
第 3 步  内存 carve：dd /proc/pid/mem + 设备侧 grep 魔数 → 拉回 → jadx
第 4 步  定位目标（网络库拦截器 / 业务类 / JNI 边界）
第 5 步  从**业务自己的** .so 或 Java 层拿密钥/算法（别碰加固库）
第 6 步  算法验证：**把服务端当判定器**做对照实验，错误码分层定位
第 7 步  自测闭环：最小 body 试边界（服务端通常比 App 宽松）
第 8 步  交付工具化，并把证据（哈希、日志、抓包）落盘归档
```

**三条铁律**：

1. **不要在你弱势的维度上硬碰**（壳强在 native/ptrace，你就换到框架层）
2. **把服务端当预言机**（错误码分层 = 免费的白盒信息）
3. **证据先于结论**（盐值要"读出来"不能"猜出来"；算法要 14/14 命中才算定）
